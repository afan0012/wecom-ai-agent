# 真实搭建复盘与踩坑

这篇记录的是把“企业微信客服 + 大模型 + 公开知识库”从空白搭到可用状态时，最容易卡住的环节。所有域名、账号、IP、密钥和客户数据都已泛化或省略。

## 目标并不是“做一个聊天接口”

真正交付的是一个外部用户能用的入口：用户扫二维码或打开客服链接，在微信里提问；机器人只根据审核过的资料回答；遇到私人决定、报价或未公开信息时交给主人确认。

因此要同时完成四件事：公网 HTTPS、企业微信回调、可靠的消息消费、大模型与知识库边界。只把大模型 API 跑通，远远不够。

## 坑 1：公网 IP 可以测试，正式回调要用 HTTPS 域名

一开始很容易想直接把公网 IP 填进回调地址。实际部署时应先准备域名：

1. DNS 添加 A 记录指向服务器公网 IPv4；
2. 云防火墙放行 80/443；
3. Caddy 或 Nginx 申请 TLS 证书；
4. 先验证 `/healthz` 可通过 HTTPS 访问；
5. 再到企业微信保存回调 URL。

DNS 控制台常会提示“最长 24–48 小时生效”。这是一种保守上限；只要权威 DNS 已更新，许多网络会更快生效。不要只等提示时间，应直接测试域名解析和 HTTPS 健康检查。

## 坑 2：香港/海外服务器与 ICP 备案是两回事

香港或海外实例可以承载企业微信回调，只要域名与 HTTPS 可访问。中国大陆 ICP 备案则需要按接入商要求使用中国大陆资源和备案流程。

不要把“能否部署客服机器人”和“是否需要大陆备案”混成一个问题。对一个仅使用海外/香港服务器的回调服务，优先保障 HTTPS、稳定性和合规内容；若后续要面向中国大陆公开运营网站，再单独评估备案。

## 坑 3：企业微信后台能打开，不等于 API 回调能通过

配置“接收消息服务器”时，企业微信会发出带签名的 GET 校验请求。后端必须：

1. 校验 `msg_signature`；
2. 解密 `echostr`；
3. 在短时间内原样返回明文。

常见失败原因不是代码本身，而是：Token 或 EncodingAESKey 与后台不一致、CorpID 写错、反向代理没有转发查询参数、HTTPS 证书不可信、80/443 被云防火墙阻断。

**经验：** 先从服务器外部访问 `/healthz`，再查看 systemd 日志，最后才修改企业微信参数。不要为了“试一下”反复更换 Token，容易把正确的本地配置和后台配置弄得不一致。

## 坑 4：微信客服不是“收到回调正文后立刻回复”

微信客服回调告诉后端“有新事件”，服务端还需要拿回调 Token 调用 `kf/sync_msg` 拉取实际消息，再调用 `kf/send_msg` 回复。

因此回调服务需要尽快返回 `success`，把同步、模型调用和回复放到后台任务中。否则模型响应稍慢时，企业微信会认为回调失败并重试，造成重复处理风险。

## 坑 5：首次接入会拿到历史消息，必须先建立游标

这是最隐蔽也最容易让客户困惑的问题。

`sync_msg` 使用游标拉取增量。如果代码没有持久化游标，服务重启或首次接入时可能把此前的会话重新读到，再给旧消息补发 AI 回复。

本仓库的处理原则是：

- 用 SQLite 保存每个客服账号的同步游标；
- 记录已处理消息 ID；
- 第一次收到该客服账号的同步结果时，只建立检查点，不回复这批历史消息；
- 同一个客服账号加异步锁，避免并发回调重复同步。

**代价：** 首次部署后需要让测试用户再发送一条新消息，之后才能验证机器人回复。这是正确的安全行为，不是故障。

## 坑 6：模型的 token 上限，不等于微信客服的发送上限

模型可以生成很长的内容，但微信客服还有平台限制：文本单条最大 2048 UTF-8 字节；客户一次主动动作对应的回复条数也有限。

正确做法不是把模型 `max_tokens` 压到很低，而是：

- 允许模型生成足够完整的答案；
- 后端按 UTF-8 字节安全切分；
- 最多发送规定条数；
- 超出时给出明确的结束提示；
- 在系统提示词中要求避免无必要的超长回答。

这样中英文和 emoji 都不会被粗暴截断，也不会因为第六条消息被平台拒绝。

## 坑 7：原生“机器人知识库”和 API 管理的客服账号会互相让人困惑

企业微信界面里既有原生机器人/欢迎语/知识库，也有“通过自建应用管理会话消息”。一旦客服账号交给自建应用 API 管理，原生页面的一些接待规则可能显示为不生效。

如果用户仍收到电商式“订单、退款、物流”开场白，应先确认它来自哪里：

- 原生欢迎语；
- 原生机器人；
- 自建应用后端的大模型提示词；
- 旧消息或重复消费。

不要盲目在多个页面同时修改。先确定该账号当前由谁接管，再修改唯一有效的配置来源。

## 坑 8：知识库需要“审核流”，不是把所有资料一股脑喂给模型

公开主页、作品文案和演示案例容易被模型误读为真实履历、业务能力或报价承诺。

推荐目录结构：

```text
knowledge/
├── drafts/      # 抓取/整理后，等待人工审阅
└── approved/    # 明确可对外引用的资料
```

每份资料应写清：来源、日期、可对外说明的事实、不能推断的事实。机器人只能读 `approved/`，并且提示词要明确：演示数据、示例企业、未确认合作都不能当成真实承诺。

## 坑 9：开源前，隐私审计不只查 API Key

还要排除：QQ 邮箱和其他邮箱、手机号、真实域名/IP、企业微信 ID、客服账号 ID、二维码、后台截图、服务日志、SQLite 数据库、抖音/网页临时 Cookie，以及 Git 提交者邮箱。

本仓库采取的默认措施：

- `.env`、数据库、日志、图片、截图、输出目录和临时工具被 `.gitignore` 排除；
- Git 提交使用通用名称和 GitHub noreply 地址；
- 文档统一使用 `bot.example.com`、`example.com` 和占位符；
- 发布前对暂存区做“仅报告位置、不显示内容”的敏感信息扫描。

## 下一步可以怎么演进

1. 在企业微信后台配置真实接待人员，再实现 API 转人工；
2. 为知识库增加引用卡片、来源链接与人工纠错入口；
3. 替换轻量关键词检索为向量检索或 RAG 服务；
4. 增加限流、错误告警、备份和健康监控；
5. 如果目标转为内部办公，另建企业微信官方“智能机器人”，不要和外部微信客服混用。
